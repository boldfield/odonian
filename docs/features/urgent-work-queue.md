# Work queue priority and move to front

## Intent

The owner needs to move time-sensitive research ahead of queued work without reducing research quality. Every topic has one positive integer priority P, default 500. Higher P runs first. Equal P uses task created_at ascending, then task ID ascending for deterministic ties. These are the only ordering keys. There is no urgent flag, special front token, front timestamp, extra priority tier or automatic aging.

Priority is scheduling metadata, separate from state and research allowance. It changes what eligible work is selected next. It does not interrupt running sessions or manufacture capacity.

## Input validation versus ordering

Explicitly supplied priorities must satisfy 0 < P <= 1000. Enforce this at all externally writable entry points, including task creation if it accepts priority and the priority setter. Omitted priority defaults to 500. Reject zero, negatives, fractions, overflow and explicit values greater than 1000; do not clamp. Reset to default is ordinary assignment of 500 through the same validation.

Move to front is a separate operator action: the server atomically computes max(1000, max(P_queued)) + 1 and assigns that numeric value to the selected topic. It always exceeds 1000. Clients cannot submit an out-of-range value disguised as move-to-front: that action accepts no numeric override. The value is computed solely by the server. If the queue maximum is 500 or 730 the result is 1001; if it is 1000 the result is 1001; if it is 1042 the result is 1043. The 1000 floor ensures that any later manually assigned priority, including 1000, cannot overtake a moved-to-front topic. A subsequent Move to front action can deliberately overtake it. The floor affects only value generation; scheduling has no special priority-band behavior.

The maximum is server-wide across outstanding topics in the queue, not the current board, worker, project or model filter. Outstanding includes backlog, held and dependency-blocked topics as well as ready, in-flight and waiting-review topics; those priorities still determine later work. Exclude archived tasks and terminal tasks, except that an unfinished descendant contributes its inherited topic priority even if the anchor is done. A topic is outstanding when any non-archived task in its execution lineage is nonterminal. The selected outstanding topic participates in the maximum. If no outstanding topic exists, reject the action rather than prioritize a wholly completed topic. A normal setter may reset a retained topic anchor without reviving it.

Read maximum and assign in one serialized database transaction. Simultaneous actions receive successively higher values. Each action carries a stable idempotency key: replay returns its original result without changing priority; a distinct action computes a fresh maximum. Reject idempotency reuse with a different payload. Persist numeric values using an integer representation large enough for generated values, preserve them exactly over API/CLI/TUI boundaries, and fail explicitly and atomically at representation overflow. Never wrap, truncate, clamp or silently renumber the queue. Internally inherited or reloaded priorities above 1000 remain valid; they must not pass through the manual-entry validator.

## Topic behavior and controls

A topic is the selected implementation task and its execution lineage: reviews, adjudications, same-task rework, superseding replacements, merge work and approved continuation descendants. An action on a descendant resolves that topic and reports its anchor. This is not every task sharing a document/project. Unrelated prerequisites, siblings, arbitrary dependents and optional non-blocking finding follow-ups are not reprioritized. Prioritize independent topics separately.

Both existing and future linked work reflect the latest topic priority, including server-generated values above 1000. Setting P back to 500 resets the whole topic; it does not rewrite timestamps, results, leases, holds or task state. A completed ancestor can anchor active continuations. Persist topic identity durably using known lifecycle relations, not title matching or arbitrary dependency traversal. Existing pre-feature lineages must work when first reprioritized. Model-generated artifacts and continuation manifests cannot invent priority, and the fleet does not issue priority changes autonomously.

Proposed CLI: odonian priority <task-id> --set <P>, --front, or --reset, exactly one operation. --reset is shorthand for --set 500. Require an operator reason and record an audit event with action, previous/resulting priority and actor using existing attribution facilities. Unique task prefixes work as with existing commands. Expose effective numeric P and topic anchor in task list/detail data. The TUI displays P directly, provides Set priority, Move to front and Reset to 500 actions, and preserves values above 1000 without clamping them to the input range. Held cards show both P and HELD; blockers remain visible. No global position or ETA that ignores role/model/pool restrictions.

## Dispatch semantics

Across all projects allowed to a worker, compare eligible tasks by P descending, created_at ascending, ID ascending. Apply that comparator uniformly at every numeric value, including P <= 1000 and P > 1000. Eligibility filters still restrict worker kind, supported/available model, project allowlist, holds, readiness, dependencies and local admission deferrals. The existing multi-project project shuffle must no longer defeat numeric order or oldest-first ties, including when every task has default P = 500. This deliberately changes equal-priority multi-project dispatch to oldest-first. Display queued cards with the same comparator; do not silently restore title ordering for ties.

Selection survives server/worker restarts and applies to actual single-project and multi-project launcher paths, CLI next and TUI. A quota-denied or unavailable high-priority task does not prevent eligible work on another pool: continue selection, respect existing retry deferrals, and reconsider the higher-priority task when eligible. Preserve research's exact-task atomic preclaim/permit before model launch, completion reservations, idempotency and ownership fencing. Refresh after claim races. The selected task must not be lost by a second lower-priority next operation.

A priority update never revokes an existing claim or live lease. Priority applies at the next refreshed scheduling decision; it is not instantaneous preemption across workers. Explicit by-ID claims retain their existing contract. Priority never bypasses holds, readiness, dependencies, account limits, reviews or merge/publication gates. Raising a held/backlog topic neither releases nor promotes it. No prerequisite priority donation in this release; show blockers. Existing research holds stay unchanged. Evaluation jobs remain separate from production topic priority.

Continually adding higher-priority work can starve lower-priority work. Keep this explicit rather than inventing aging exceptions. Numeric setting/reset gives the operator control.

## Acceptance and tests

- API/CLI creation and manual setter accept 1, 500 and 1000, reject 0, negative/fractional/overflow and 1001; omission defaults to 500. Existing callers not setting priority remain compatible.
- Front computes exactly max(1000, max(P_queued)) + 1 at maxima below, at and above 1000. Test 500->1001, 730->1001, 1000->1001 and 1042->1043. After moving a topic from a queue maximum of 500, create later tasks at 505 and 1000: neither may overtake it; a subsequent Front action may. Filters, held tasks and waiting/blocked topics do not hide the true maximum. Wholly terminal or archived topics do not inflate it. A done anchor with active descendants still contributes through them.
- Concurrent front requests serialize; retrying an action does not reorder it. Overflow fails without any state changes. Restarts and JSON/CLI/TUI round trips preserve generated values exactly.
- With older low-priority work in project A and a newly higher-priority task in project B, multi-project selection chooses B. Equal priorities choose oldest task across projects, with deterministic ID ties. There is no separate front sequence or special priority-band ordering.
- Existing/future reviews, rework, adjudications, replacements, merges and continuation generations follow topic priority above 1000; setting/resetting via a descendant updates them. Unrelated topics and optional follow-ups stay at their existing priority.
- Held, dependency-blocked, not-ready, unavailable-model and quota-denied high-priority tasks stay ineligible without stalling otherwise eligible work. Completion reservations cannot be spent by a high-priority new writer. Concurrent claims cannot double-charge permits or duplicate ownership. Running tasks are never interrupted.
- The TUI shows numeric P alongside HELD; manual entry is bounded but displaying and inheriting generated values is not. API, CLI next, queued-card sorting and fleet selection agree on the comparator.
- End-to-end smoke uses a temporary server/database, two projects, real fleet selection and fake model processes. No paid calls, production deployment, live reprioritization or release of research holds during implementation validation.
